# 🌐 Deploy RouteOS to a free public URL

This gives you a shareable live demo without paying, on two free services that do not expire:

- **[Neon](https://neon.tech)**: the PostgreSQL + PostGIS database.
- **[Render](https://render.com)**: Redis, the backend API and the frontend, from [`render.yaml`](render.yaml).

> **Why not Render's own free Postgres?** It is deleted 30 days after creation (plus a 14-day
> grace period). That is what took the first live demo down: the database vanished and the
> backend waited for it forever. Neon's free plan has no expiry and supports PostGIS.

> Free web services **sleep after ~15 min idle** and cold-start in ~50s. Perfect for a portfolio
> demo; not for production traffic.

## Steps

### 1. Create the database on Neon (once)

1. Sign up at **https://neon.tech** (free, no card) and create a project, e.g. `routeos`.
   Pick the region closest to your Render region (Render's default is Oregon → `us-west-2`).
2. On the project dashboard click **Connect**. Turn **Connection pooling off**: the backend
   uses asyncpg, which works best with a direct connection.
3. Copy the connection string. It looks like
   `postgresql://neondb_owner:…@ep-xxxx.us-west-2.aws.neon.tech/neondb?sslmode=require&channel_binding=require`.
   Paste it exactly as given; the backend converts it for both of its database drivers.

PostGIS is switched on by the first migration (`CREATE EXTENSION IF NOT EXISTS postgis`);
Neon allows that, so there is nothing to enable by hand.

### 2. Deploy on Render

1. Go to **https://render.com** → sign up (free) → **New ➜ Blueprint**.
2. **Connect the repo.** Render detects [`render.yaml`](render.yaml) and lists 3 resources:
   `routeos-redis`, `routeos-backend`, `routeos-frontend`.
3. It asks for **`DATABASE_URL`**: paste the Neon string from step 1.
4. Click **Apply**. Render builds and deploys everything (first deploy ~5–8 min).
5. Open the **frontend** URL Render gives you and sign in with
   `dispatcher@routeos.dev` / `dispatch12345`.

### Already deployed, and the Render database expired?

The backend is stuck waiting for a database that no longer exists. Keep the services; swap the
database:

1. Create the Neon database (step 1 above) and copy its connection string.
2. In Render, open **routeos-backend → Environment**, set **`DATABASE_URL`** to the Neon string,
   and click **Save, rebuild and deploy**.
3. Delete the expired **routeos-db** under **Databases** (it cannot be revived on the free plan).

The backend's entrypoint creates every table and seeds the demo data on the new database by itself.

The backend's Docker entrypoint runs migrations and seeds demo data automatically on first boot,
exactly like it does locally.

## No manual URL wiring needed

Earlier versions of this blueprint hard-coded `https://routeos-backend.onrender.com`, which broke
whenever Render appended a suffix to a service name (it does that when a name is already taken
globally). That is fixed — every cross-service URL now resolves through `fromService`:

| Consumer | Variable | Source |
|---|---|---|
| Frontend | `VITE_API_HOST` | the backend service's hostname |
| Backend | `BACKEND_CORS_ORIGIN_REGEX` | pattern matching the deployed frontend |
| Backend | `DATABASE_URL` | your Neon connection string (pasted once; `sync: false`) |
| Backend | `REDIS_URL` | the Key Value connection string |
| Backend | `SECRET_KEY` | generated by Render |

`fromService` with `property: host` resolves to the peer's **service name**
(e.g. `routeos-backend-h5x6`) — Render's internal DNS name, not a public FQDN. The frontend bundle
runs in a browser, so it expands a dot-less value to `<name>.onrender.com` and derives `https://`
and `wss://` from it (see [`frontend/src/api/client.ts`](frontend/src/api/client.ts)). A value that
already contains a dot is treated as a real hostname and used as-is, so a custom domain works too.

To point the frontend somewhere else entirely, set `VITE_API_BASE_URL` and `VITE_WS_BASE_URL` to
full origins — they take priority over `VITE_API_HOST`.

CORS is matched by **pattern** rather than by naming the frontend service, because the frontend
already references the backend and Render rejects circular blueprint dependencies. The backend
therefore allows `^https://[a-z0-9-]+\.onrender\.com$`, which holds whatever suffix Render assigns.
Starlette echoes back the specific matched origin (never a wildcard), so credentialed requests stay
spec-compliant. For a custom domain, set `BACKEND_CORS_ORIGINS` to it as well — scheme-less entries
are expanded to `https://<host>` (see [`backend/app/core/config.py`](backend/app/core/config.py)).

**You do not need to edit anything before or after deploying.**

## Notes & gotchas

- **PostGIS** is created by the first Alembic migration (`CREATE EXTENSION postgis`). Neon
  allows it, so no superuser action is needed.
- **Database URL**: Neon hands out a standard `postgresql://…?sslmode=require&channel_binding=require`
  string. The backend turns it into the async (`+asyncpg`, with `ssl=require`) and sync
  (`+psycopg`, with `sslmode=require`) driver URLs automatically.
- **Cold starts**: the first request after idle wakes the API; give it ~50s.
- **Custom domain**: add one on the frontend service; the backend's CORS follows the service
  hostname, so add your custom domain to `BACKEND_CORS_ORIGINS` as an extra comma-separated value
  if you use one.

## Troubleshooting a failed deploy

Open the **routeos-backend** service → **Logs**, and match the last line before it died:

| Log line | Cause | Fix |
|---|---|---|
| `Postgres at postgres:5432 never became reachable` | The container is resolving the *compose* hostname instead of the managed database. | Fixed — the entrypoint now parses the host out of `DATABASE_URL`. Make sure `DATABASE_URL` is set on the service (the Neon string you pasted). |
| Health check never passes / `no open ports detected` | The app is bound to a port the platform isn't routing to. | Fixed — the image binds `$PORT` and falls back to 8000. |
| `CREATE EXTENSION postgis` permission denied | The database isn't a PostGIS-capable instance. | Neon and Render Postgres both allow PostGIS. On another host, check that PostGIS is available to your role. |
| `unexpected keyword argument 'sslmode'` | An older backend build passed Neon's libpq options to asyncpg. | Fixed: the backend now translates `sslmode`/`channel_binding` for asyncpg. Redeploy from `master`. |
| Backend never answers; logs show `Waiting for Postgres…` then exit | `DATABASE_URL` points at a database that is gone (e.g. an expired Render free Postgres). | Follow *Already deployed, and the Render database expired?* above. |
| Build killed / out of memory | `ortools` is a large wheel and free build instances are small. | Retry the deploy; if it persists, upgrade the build instance temporarily for the first build. |

After pushing a fix, use **Manual Sync** on the Blueprint (or **Manual Deploy → Clear build cache
& deploy** on the backend) to pick up the new commit. Because the first deploy failed, the
frontend was cancelled — re-syncing creates it once the backend is healthy.

## Other hosts

The same four services deploy just as well on **Railway** or **Fly.io** — provide
`DATABASE_URL`, `REDIS_URL`, and the frontend build var (`VITE_API_HOST`, or
`VITE_API_BASE_URL` + `VITE_WS_BASE_URL` if you prefer full origins).

## Prefer zero cloud setup?

For most reviewers the simplest path is still local — one command, everything included:

```bash
cp .env.example .env
docker compose up --build
# → http://localhost:5173
```
